# Reduced graphics for the Amiga 68k port — implementation plan

Status: **plan only**. No source file has been changed. Written 2026-07-20.

Reader: whoever implements this, possibly months later with no memory of the
conversation that produced it. Everything load-bearing is cited to a file and a
line number in `upstream/openttd-1.0.5/src` or `native/openttd`.

Goal as stated: let the player pick a graphics set at startup — full size, or a
half-size lores set — so the lores set is what actually gets loaded. **The point
is saving memory**, so the port can run on an 020 with 8 MB. Secondary: fewer
colours means fewer bitplanes and less chunky-to-planar work.

---

## 0. Summary, including three findings that change the plan

Read this section before anything else. Three things emerged from reading the
code that the original framing did not account for, and two of them redirect the
work substantially.

### 0.1 The 4 MB sprite cache is a fixed arena. Smaller sprites do not shrink it.

`GfxInitSpriteMem()` (`spritecache.cpp:561-577`) does a single
`MallocT<byte>(_sprite_cache_size * 1024 * 1024)` and lays the whole block out
as one free `MemBlock`. It is allocated **once** — the `if (_spritecache_ptr ==
NULL)` guard at `spritecache.cpp:564` means changing the setting requires a
restart — and it never grows or shrinks. `_sprite_cache_size` defaults to 4
(`spritecache.cpp:25`; config entry `sprite_cache_size` in `[misc]`,
`table/settings.h:273`, range 1–64 MB).

Sprites are decoded **lazily**, on first draw, not at startup. `LoadNextSprite`
(`spritecache.cpp:269-298`) records only a file offset and sets `sc->ptr = NULL`;
`GetRawSprite` (`spritecache.cpp:533-558`) decodes on demand and
`DeleteEntryFromSpriteCache` (`spritecache.cpp:415-451`) evicts by LRU when the
arena fills.

So halving sprite dimensions does **not** by itself save a single byte. It
reduces *pressure* on a fixed arena — more sprites fit, fewer evictions. The
memory is only banked when you **also lower `sprite_cache_size`**, and the whole
value of the lores set is that it makes a 1 MB arena behave like a 4 MB one.

**Both halves must ship together.** A lores set without a lowered
`sprite_cache_size` saves nothing; a lowered `sprite_cache_size` without lores
sprites just thrashes.

### 0.2 The binary dominates the budget, and graphics work cannot fix it

`winuae/work/openttd-w0` is 5,174,152 bytes. AmigaDOS `LoadSeg()` reads the
whole thing into RAM before the first instruction runs. `PROGRESS.md` records
that `m68k-amigaos-strip` produces an executable that halts the CPU, so the
symbol tables cannot currently be removed.

That is 5.17 MB gone before OpenTTD allocates anything. Section 8 does the full
arithmetic; the short version is that on 8 MB of Fast RAM, after the binary, the
1 MB stack (`__stack` is set to 1 MB by `build/apply-amiga-patches.py`), the
sprite index array and a 256×256 map, there is roughly **0.5–0.7 MB left for the
sprite cache**. The lores set is exactly what makes that survivable — but it is
the second-largest lever, not the largest. **Shrinking the binary is the
first-order problem.** See section 8.3 for what to try.

### 0.3 There is a much cheaper way to get the same memory saving: zoom levels

`Blitter_8bppOptimized::Encode` (`blitter/8bpp_optimized.cpp:111-194`) builds and
caches **all four zoom levels for every sprite, unconditionally**:

```c
for (ZoomLevel i = ZOOM_LVL_BEGIN; i < ZOOM_LVL_END; i++) {
    memory += UnScaleByZoom(sprite->height, i) * UnScaleByZoom(sprite->width, i);
}
```

The four levels have relative pixel areas 1, 1/4, 1/16, 1/64 — total 1.328. The
zoom-1 level is generated by nearest-neighbour decimation
(`8bpp_optimized.cpp:148-159`: "pick any non-transparent pixel in the block").

This matters enormously, because **a half-size GRF rendered at zoom 0 and a
full-size GRF rendered at zoom 1 produce the same number of screen pixels and
the same cache footprint.** OpenTTD already has the entire mechanism. The
differences are:

|  | lores GRF | forced zoom 1 |
|---|---|---|
| image quality | Lanczos with edge bleed, hand-tuned | nearest neighbour, "any non-transparent pixel" |
| asset work | rebuild 6 GRFs, solve the `.nfo` geometry problem | none |
| geometry breakage | offsets, bboxes, tile grid, cursors, fonts, GUI | none — it is a supported feature |
| UI size | shrinks with the world unless sprites are split | stays full size and readable |
| cache saving | needs no engine change | needs `Encode` changed to stop building unused levels |

The catch: forcing the viewport to zoom 1 saves nothing on its own, because
`Encode` still builds level 0. And you cannot simply skip level 0 globally — the
UI is drawn through `_screen`, whose `DrawPixelInfo::zoom` is `ZOOM_LVL_NORMAL`
(`gfx.cpp:1607`), and `GfxMainBlitter` passes `dpi->zoom` straight to
`Blitter::Draw` (`gfx.cpp:1125`). Widget and font sprites genuinely need level 0.

The correct form is therefore **lazy per-zoom encoding**: build a zoom level the
first time it is asked for, not all four up front. That is Phase 0 below, it is
independent of every asset decision, and it should be done first because it is
cheap, reversible, and measurable.

### 0.4 The resulting shape of the work

| Phase | What | Cost | Memory won |
|---|---|---|---|
| 0 | Lazy per-zoom sprite encoding + optional forced min zoom | small, engine-only | large (≈4× on world sprites) |
| 1 | Lores 256-colour GRF, selectable at startup | large, mostly asset pipeline | same ≈4×, better quality |
| 2 | Output LUT + variable bitplane count | medium | none — this buys *speed*, not RAM |
| 3 | Recolouring the interface for a small palette | large, mostly artwork | none |

Phases 0 and 1 are alternative routes to the same saving. Phase 0 is a strictly
better first move; Phase 1 is what you do if the quality of Phase 0 is not good
enough, and the two can coexist (a lores GRF with lazy zoom encoding is the
smallest possible configuration).

**Size reduction is a load-time / asset-time problem. Colour reduction is an
output-time problem.** They are different, they are solved in different places,
and conflating them is the main way this work goes wrong. Section 4 explains
why.

## 1. Where the bytes actually are

Measured or read from source; estimates marked as such.

| Consumer | Size | Where |
|---|---|---|
| Binary, via `LoadSeg` | **5,174,152 B** | `winuae/work/openttd-w0`, measured |
| Stack | **1 MB** | `__stack` set in `build/apply-amiga-patches.py` |
| Sprite cache arena | **4 MB** default | `spritecache.cpp:25`, `:561-577` |
| `SpriteCache` index array | ≈ *n* × 20 B, **est. 300–400 KB** | `spritecache.cpp:29-37`, grown 1024 at a time by `AllocateSpriteCache` `:54-70` |
| Map | 10 B/tile → **655 KB** at 256², **2.6 MB** at 512² | `Tile` + `TileExtended` |
| Chunky framebuffer (Fast) | 320×256 = 80 KB; 640×512 = 320 KB | `amiga_gfx.c:94` |
| Bitplanes (**Chip**) | 320×256×8 = 80 KB; 640×512×8 = 320 KB | `amiga_gfx.c:97` |
| Language pack, strings, windows, vehicles, towns | est. 200–400 KB | — |

Two notes that matter:

- The **index array scales with sprite count, not pixel area.** A lores set has
  exactly the same number of sprites, so this 300–400 KB does not shrink at all.
  It is a floor. (`struct SpriteCache` is `void* + size_t + uint32 + uint16 +
  int16 + byte + bool`, `spritecache.cpp:29-37` — 18 bytes, 20 after m68k
  alignment. The sprite count for OpenGFX 0.4.7 is an estimate; measure it with
  `-d grf=1` and read the highest load index reported by `LoadSpriteTables`.)
- **Bitplanes live in Chip RAM, everything else in Fast.** On an A1200-class
  machine with 2 MB Chip + 8 MB Fast these are separate budgets, which helps.
  Section 8 gives both readings.

## 2. Phase 0 — lazy per-zoom sprite encoding

Do this first. It is engine-only, needs no assets, breaks no geometry, and is
worth roughly a 4× reduction in world-sprite cache pressure.

### 2.1 What to change

`Blitter_8bppOptimized` stores all four levels in one allocation, indexed by
`SpriteData::offset[ZOOM_LVL_END]` (`blitter/8bpp_optimized.hpp`). The change is
to make the encode per-level and let the sprite cache hold one entry per (sprite,
zoom) pair.

Two implementation options, in increasing order of invasiveness:

**Option A — encode-mask (simple, partial).** Add a global
`ZoomLevel _min_encoded_zoom` and skip levels below it in the two loops at
`8bpp_optimized.cpp:115-118` and `:130-134`, writing `offset[i] = offset[first]`
for the skipped ones so nothing indexes out of range. Then set the mask per
sprite type: level 0 is required for `ST_FONT` and for any sprite drawn through
`_screen` (UI), not for world sprites. The difficulty is that you cannot tell at
`Encode` time whether a sprite will ever be drawn at zoom 0 — `Encode` is called
from `ReadSprite` (`spritecache.cpp:256-265`) with no context. You would have to
approximate by sprite-ID range, which is fragile: GUI sprites are scattered
across `table/sprites.h` and NewGRF sprites live above `SPR_NEWGRFS_BASE`.

**Option B — lazy per-zoom (correct, recommended).** Extend the cache key from
`SpriteID` to `(SpriteID, ZoomLevel)` and encode on demand:

1. `struct SpriteCache` (`spritecache.cpp:29-37`) gains a per-zoom `void
   *ptr[ZOOM_LVL_COUNT]` in place of the single `ptr`, or the index array is
   simply widened to `ZOOM_LVL_COUNT` entries per sprite. The latter multiplies
   the index array by 4 — 1.2–1.6 MB — which is unacceptable on this target, so
   use a 4-pointer struct (adds 12 B/sprite ≈ 240 KB, still significant; consider
   packing to two levels if only two are reachable).
2. `GetRawSprite` (`spritecache.cpp:533-558`) takes the zoom level and returns
   the per-zoom pointer, calling `ReadSprite` only for the missing level.
3. `ReadSprite` (`spritecache.cpp:145-266`) passes the level down; `Encode` gains
   a `ZoomLevel` parameter and emits exactly one level.
4. `Blitter::Draw` (`blitter/8bpp_optimized.cpp:29+`) stops indexing
   `offset[zoom]` and reads the single stored level.
5. `DeleteEntryFromSpriteCache` (`spritecache.cpp:415-451`) and
   `CompactSpriteCache` (`:375-413`) must walk the per-zoom pointers.
6. `GfxMainBlitter` (`gfx.cpp:1044-1126`) already has `dpi->zoom`; the call chain
   from `DrawSprite` → `GetSprite` (`spritecache.h:31-35`) does not, so the zoom
   has to be threaded through, or `GetSprite` keeps returning the level-0
   *metadata* (width/height/offsets — which is what every caller actually reads)
   while the pixel data is fetched per-zoom inside the blitter.

Point 6 is the crux and the reason Option B is a day's work rather than an
hour's: `Sprite` (`spritecache.h:18-24`) carries both metadata and pixel data,
and roughly a hundred call sites read `->width`, `->height`, `->x_offs`,
`->y_offs` while never touching `->data`. Keep metadata at level-0 semantics —
that is what the rest of the engine assumes — and make only the pixel payload
per-zoom. Done that way, nothing outside `spritecache.cpp` and the blitters needs
to change.

### 2.2 Optionally force the minimum zoom

If the world should render at half size (matching what the lores set would look
like), edit `zoom_type.h:30-43`. The relevant constants are all in that one
block:

```c
ZOOM_LVL_VIEWPORT = ZOOM_LVL_NORMAL,   // line 31 -> ZOOM_LVL_OUT_2X
ZOOM_LVL_NEWS     = ZOOM_LVL_NORMAL,   // line 32
ZOOM_LVL_AIRCRAFT = ZOOM_LVL_NORMAL,   // line 35
ZOOM_LVL_SHIP     = ZOOM_LVL_NORMAL,   // line 36
ZOOM_LVL_TRAIN    = ZOOM_LVL_NORMAL,   // line 37
ZOOM_LVL_ROADVEH  = ZOOM_LVL_NORMAL,   // line 38
ZOOM_LVL_MIN      = ZOOM_LVL_NORMAL,   // line 42
```

`ZOOM_LVL_MIN` gates zoom-in only, at `main_gui.cpp:140`, `:178` and
`viewport.cpp:460`; `waypoint_gui.cpp:59` passes it explicitly. Raising it to
`ZOOM_LVL_OUT_2X` costs one file and is fully reversible. The vehicle-view
constants control the little viewports in vehicle windows; leave them at
`ZOOM_LVL_NORMAL` if you want vehicle detail readable, at the cost of keeping
level 0 cached for vehicle sprites.

Note this makes the world small **while the UI stays full size and readable** —
which is the outcome Phase 3 is otherwise trying to buy with artwork.

### 2.3 How to measure it

`GetSpriteCacheUsage()` (`spritecache.cpp:332-342`) already sums the allocated
blocks. Log it once per 200 frames next to the existing blit statistics in
`ReportBlitStats()` (`amiga_v.cpp:251-264`), then run the same savegame with and
without the change. Do not accept the estimate — measure. If usage does not drop
by roughly 4× on a world-heavy view, the change is not doing what it should.

## 3. Phase 1 — the lores 256-colour set

### 3.1 The `.nfo` geometry problem, and why the current sheets cannot be used

`gfxdump/README-lores.txt` states the known gap correctly: the sheets are half
size, so every sprite coordinate and every x/y offset in the `.nfo` files must be
halved before `grfcodec -e` can rebuild a usable GRF. There is a second problem
underneath it that is more serious.

A grfcodec real-sprite line has the form

```
<num> <pcxfile> <xpos> <ypos> <compression> <ysize> <xsize> <xrel> <yrel>
```

so the naive transformation is to halve `xpos`, `ypos`, `xsize`, `ysize`, `xrel`,
`yrel`. That fails for four independent reasons:

1. **The master sheet was downscaled as a single 5600×16000 image, ignoring
   sprite boundaries.** A sprite whose `xpos` or `ypos` is odd lands on a
   half-pixel in the output; its content is averaged across the boundary with
   whatever is next to it in the sheet. Worse, the "bleed opaque colours outwards
   a few pixels before Lanczos" step described in `README-lores.txt` bleeds each
   sprite into its *neighbours*, not into empty margin, wherever grfcodec packed
   sprites tightly. This is invisible at a glance and fatal in game.

2. **Odd dimensions do not halve.** A 1-pixel-wide sprite becomes 0 and must be
   clamped to 1; a 3-pixel sprite rounds to 2. Small GUI and overlay sprites are
   full of odd sizes, and the clamping desynchronises size from offset.

3. **Offset rounding direction has to match the content.** `xrel` is usually
   negative. Halving −31 gives −15.5, and whether you round toward zero or away
   determines whether the sprite sits half a lores pixel left or right of where
   its neighbours expect it. For scenery this is tolerable; for ground tiles it
   produces visible seams across the whole landscape.

4. **Ground and tile sprites must be exact.** A 64×31 ground tile has to become
   exactly 32×16 (or 32×15) with offsets that still tile perfectly, or the
   terrain shows a lattice of gaps.

**Recommendation: throw away the whole-sheet downscale and rebuild the pipeline
per sprite.** Concretely:

1. Re-run `grfcodec -d -t` on each of `winuae/work/data/ogfx*.grf` to regenerate
   the `.nfo` files (they are not currently in the repo; `README-lores.txt` says
   they were in `/tmp/grfdump`, which is gone). Keep them under version control
   this time — `gfxdump/nfo/`.
2. Parse each `.nfo`. For every **real** sprite, crop exactly
   `(xpos, ypos, xsize, ysize)` out of the decoded sheet.
3. Run the existing bleed → Lanczos → separate mask resize → 50% coverage cut on
   **that crop alone**, so bleeding goes into genuine empty space and never into
   a neighbour.
4. Emit the result into a **new sheet on a fresh layout**, with generous padding
   and even-aligned positions chosen by the packer, not inherited.
5. Emit a **new `.nfo`** with the new `xpos`/`ypos`, the actual output
   `xsize`/`ysize`, and `xrel`/`yrel` scaled about the sprite's anchor with one
   documented rounding rule.
6. `grfcodec -e` to rebuild the GRF.
7. Special-case the sprites listed in 3.2 — pass them through at original size.

This is more work than patching numbers in the existing `.nfo`, and it is the
only version that produces a correct GRF. Budget it as the largest single item in
Phase 1. Treat `gfxdump/lores-256.png` as what `README-lores.txt` honestly calls
the 32-colour set — "a look-and-see pass" — and not as a shippable asset.

### 3.2 What must NOT be halved

These are hard exclusions. Halving any of them breaks the game rather than making
it look small.

- **`ST_MAPGEN` sprites.** `landscape.cpp:716` reads sprites around ID 4845 via
  `GetSprite(..., ST_MAPGEN)`. `ReadSprite` (`spritecache.cpp:221-252`) decodes
  these as raw uncompressed data and their `width`/`height` are consumed as **map
  generation dimensions, not pixels**. Halving them changes terrain generation.
  Range guarded by `IsMapgenSpriteID` (`spritecache.cpp:281`).
- **`ST_RECOLOUR` sprites, IDs 0x307–0x316 and neighbours.** These are 257-byte
  palette remap *tables*, not images (`spritecache.cpp:184-210`,
  `RECOLOUR_SPRITE_SIZE = 257`). `SetupColoursAndInitialWindow`
  (`main_gui.cpp:402-409`) reads `+0xC6` out of each of the 16 company recolour
  sprites to build `_colour_gradient[COLOUR_END][8]` — the entire window, graph,
  smallmap and text colour scheme. grfcodec keeps them as pseudo-sprites, so they
  pass through untouched as long as the pipeline does not try to treat them as
  bitmaps.
- **Font sprites.** `ResetFontSizes()` (`fontcache.cpp:1060-1065`) hardcodes
  `_font_height[FS_SMALL] = 6`, `[FS_NORMAL] = 10`, `[FS_LARGE] = 18`. Glyph
  *widths* are read from the sprite (`fontcache.h:81`) but heights are constants,
  so halved glyphs render 5 px tall inside 10 px boxes. And the small font is
  already 6 px — halved it is 3 px and illegible. Base sprites are
  `SPR_ASCII_SPACE`, `SPR_ASCII_SPACE_SMALL`, `SPR_ASCII_SPACE_BIG`
  (`table/sprites.h`, selected in `GetFontBase()`, `fontcache.cpp:1075-1083`).
- **GUI / widget sprites.** `window_gui.h:36-120` (`enum WidgetDrawDistances`)
  hardcodes the whole chrome geometry — `WD_VSCROLLBAR_WIDTH = 12` (`:48`),
  `WD_CAPTION_HEIGHT = 14` (`:103`), `WD_SORTBUTTON_ARROW_WIDTH = 11` (`:116`) —
  and `widget.cpp:1766-1784` repeats literal 12/14 values in `SetMinimalSize`
  calls. `widget.cpp:385` does `r.right - 8` assuming an 8 px arrow. Halving GUI
  sprites without also halving all of this gives a broken interface.

That leaves **world sprites** — terrain, buildings, vehicles, trees, industries,
stations — as the halving target. That is fine: they are the overwhelming
majority of pixel area, so nearly all of the memory saving survives the
exclusions.

### 3.3 What halving world sprites breaks in the engine

Investigated specifically. The good news first.

**Safe, no change needed:**

- **The viewport sorter.** `ParentSpriteToDraw` (`viewport.cpp:82-102`) sorts on
  `xmin/xmax/ymin/ymax/zmin/zmax`, which are **world** coordinates filled from
  the caller's arguments at `viewport.cpp:701-708`. No sprite dimension is
  involved. Draw order stays correct. This is the single biggest thing in your
  favour.
- **Cursor hotspots.** `UpdateCursorSize()` (`gfx.cpp:1652-1663`) reads
  `p->width`, `p->height`, `p->x_offs`, `p->y_offs` straight out of the sprite,
  so hotspots follow automatically. `struct CursorVars` is `gfx_type.h:113-137`.
  The **one** exception is `depot_gui.cpp:492` and `:496`:
  `_cursor.short_vehicle_offset = 16 - Train::From(v)->tcache.cached_veh_length * 2;`
  — the `16` and the `* 2` are raw pixels and need halving.
- **Widget sizing that calls `GetSpriteSize`** (`gfx.cpp:1013-1021`) adapts
  automatically: `widget.cpp:1828, 1839, 1850, 1870-1871, 1880`,
  `company_gui.cpp:1823, 2070`, `graph_gui.cpp:1292, 1466`, `order_gui.cpp:195,
  945`, `bridge_gui.cpp:191`, `main_gui.cpp:226, 232`.

**Broken, and this is the hard part:**

- **The isometric projection.** `RemapCoords` (`landscape.h:52-58`):
  ```c
  pt.x = (y - x) * 2;
  pt.y = y + x - z;
  ```
  That `* 2` is the only expression of "a 16-unit tile is 32 pixels wide", and
  `TILE_PIXELS = 32` (`tile_type.h:19`) is never related to `TILE_SIZE = 16`
  (`:17`) in code. Halving world sprites without halving the projection leaves
  gaps between every tile.
- **The projection is duplicated with raw shifts in at least four more places**,
  none of which share a constant with `RemapCoords`:
  - `InverseRemapCoords` (`landscape.h:81-85`): `{(y*2 - x) >> 2, (y*2 + x) >> 2}`
  - `TranslateXYToTileCoord` (`viewport.cpp:380-381`): `>> 2` and `>> 1` — this
    is the mouse-picking path, so getting it wrong makes clicks land on the wrong
    tile
  - `ViewportAddLandscape` (`viewport.cpp:1003-1010`): `>> 1`, `>> 2`, and the
    scan bounds `+ 95`, `>> 6`, `>> 5`. **These are the most fragile constants in
    the file** — 64 is two tile widths, 32 is one.
  - `viewport.cpp:1678-1686`: `TILE_PIXELS - 2` as a dirty-rect half-width,
    `OVERLAY_WIDTH = 4` at `:1683`, `- TILE_HEIGHT` at `:1686`
  - `screenshot.cpp:614-618`, `smallmap_gui.cpp:1141, 1285`
- **`TILE_HEIGHT` (`tile_type.h:20`) cannot be halved.** It is documented as a
  world Z step of 8, but because `RemapCoords` maps Z 1:1 into screen Y it is
  *simultaneously* 8 screen pixels. Halving it to 4 changes map semantics —
  `MAX_TILE_HEIGHT = 15` (`:22`), slopes, bridge clearances — and therefore
  savegame compatibility. Halving it is not an option; the vertical scale has to
  be compensated inside the projection instead, which means `pt.y` needs a divide
  where today it needs nothing. This asymmetry (X halves cleanly, Z does not) is
  the single nastiest part of Phase 1 and is easy to underestimate.
- **Child sprite anchoring.** `AddSortableSpriteToDraw` (`viewport.cpp:667-673`)
  sets `ps->left`/`ps->top` from `spr->x_offs`/`y_offs`; `AddChildSpriteScreen`
  (`viewport.cpp:762+`) receives *screen-pixel* deltas from callers that hardcode
  full-size values. Every vehicle overlay, catenary and station overlay would be
  mis-anchored. `AddCombinedSprite` (`viewport.cpp:600-613`) is worse: line 612
  mixes a full-scale `pt` from `RemapCoords` with a halved `pstd->left`.
- **`SubSprite` clipping.** `gfx.cpp:1050-1053` computes
  `clip_left = max(0, -sprite->x_offs + sub->left)`; `SubSprite` rectangles come
  from callers in full-size pixel space (bridges, tunnels, vehicles in depots),
  so the clips cut the wrong amount.
- **NewGRF sprite layouts.** `DrawCommonTileSeq` (`sprite.cpp:100`) converts
  `delta_x/y/z` through `RemapCoords`. These are world units, so they follow the
  projection — but that means they must be changed in lockstep with it, not
  independently.
- Cosmetic: `_draw_bounding_boxes` (`viewport.cpp:675-681`),
  `aircraft_cmd.cpp:213` (`y - 5` rotor offset), `viewport.cpp:844` (literal `7`).

**Assessment.** Section 3.2's exclusions plus section 3.3's projection surgery
means Phase 1 is not "load different sprites"; it is a partial rescale of the
world coordinate system with a hard-coded exception (`TILE_HEIGHT`) that does not
want to move. This is precisely the work that Phase 0 avoids entirely, because
`ScaleByZoom`/`UnScaleByZoom` (`zoom_func.h:24-43`) already handle all of it
correctly and are already exercised by every existing zoom level.

**If Phase 1 is pursued anyway, do it in this order:** get the GRF rebuilt and
loading first, look at the (wrong, gappy) result on screen, and only then start
on the projection. A rebuilt GRF that loads is a real milestone; a projection
rewrite against an asset you cannot yet load is not debuggable.

### 3.4 Telling the game to load the lores set

This part is genuinely easy — no engine change is required to make a new set
*selectable*.

A graphics set is six GRFs plus an `.obg` ini file in a `DATA_DIR` search path
(`GraphicsSet : BaseSet<GraphicsSet, MAX_GFT, DATA_DIR>`,
`base_media_base.h:240-244`; `GraphicsFileType` = base, logos, arctic, tropical,
toyland, extra, `:229-237`). `BaseGraphics::FindSets()` is called at
`openttd.cpp:565` and scans for `.obg` (`gfxinit.cpp:314-318`); each file is
parsed by `GraphicsSet::FillSetDetails` (`gfxinit.cpp:208-219`) over
`BaseSet<>::FillSetDetails` (`base_media_func.h:34-140`).

Write `winuae/work/data/opengfx-lores.obg` modelled on
`winuae/work/data/opengfx.obg`:

```ini
[metadata]
name        = OpenGFX-lores
shortname   = OGFL
version     = 1
palette     = Windows
description = OpenGFX at 50%, for low-memory 68k Amigas.

[files]
base     = ogfx1_base_lo.grf
arctic   = ogfxc_arctic_lo.grf
tropical = ogfxh_tropical_lo.grf
logos    = ogfxi_logos_lo.grf
toyland  = ogfxt_toyland_lo.grf
extra    = ogfxe_extra_lo.grf

[md5s]
...

[origin]
default = Generated by tools/mklores.py from OpenGFX 0.4.7.
```

Points that will bite:

- **`name` and `shortname` must both differ from OpenGFX's.** `BaseMedia::AddFile`
  (`base_media_func.h:161-198`) deduplicates on *either*, keeping whichever set
  has more `valid_files`. Reuse either and the lores set silently vanishes into
  `duplicate_sets`.
- **Wrong md5s are not fatal.** `CheckExternalFiles` (`gfxinit.cpp:96-137`) only
  builds a warning string and shows it via `ShowInfoF` at `:136`. Correct md5s
  just remove the nag. There is no "ignore md5" flag in 1.0.5.
- **Missing files are effectively fatal.** A set with `GetNumMissing() != 0` is
  excluded from `DetermineBestSet()` (`gfxinit.cpp:298`) and hidden from the GUI
  list (`base_media_func.h:301, 323`). All six files must exist even if some are
  copies of the originals.
- **`palette` parsing looks at the first character only** (`gfxinit.cpp:215-216`):
  `D`/`d` → `PAL_DOS`, anything else → `PAL_WINDOWS`. Match OpenGFX's `Windows`
  or every pixel gets run through `_palette_remap` at
  `spriteloader/grf.cpp:131, 156`.
- **`extra` is loaded as a NewGRF**, not as a plain sprite file
  (`gfxinit.cpp:180-193`): a temporary `GRFConfig` is built, `FillGRFDetails`
  called, pushed onto `_grfconfig`, `LoadNewGRF(SPR_NEWGRFS_BASE, i)`, then
  popped. It must remain a structurally valid NewGRF, not just a sprite dump.
- `GfxLoadSprites()` (`gfxinit.cpp:197-206`) is **not** called during
  `ttd_main` startup — the first call is from `afterload.cpp:583` /
  `genworld.cpp:299`, i.e. when the intro game loads. So a bad set fails at
  intro-game load, not at launch, and the error will look unrelated.

## 4. Phase 2 — colour reduction as an output-stage LUT

### 4.1 Why it belongs at the output stage, and nowhere else

This is the design decision that must not be revisited casually.

OpenTTD recolours vehicles and company-owned structures by **remapping palette
indices at draw time**. `DrawSprite` (`gfx.cpp:1031-1042`) fetches the remap
table and hands it to the blitter:

```c
_colour_remap_ptr = GetNonSprite(GB(pal, 0, PALETTE_WIDTH), ST_RECOLOUR) + 1;
GfxMainBlitter(GetSprite(real_sprite, ST_NORMAL), x, y, BM_COLOUR_REMAP, sub);
```

`GfxMainBlitter` puts it in `bp.remap` (`gfx.cpp:1078`) and
`Blitter_8bppOptimized::Draw` applies `bp->remap[colour]`
(`8bpp_optimized.cpp:84-97`). The company's colour is chosen by
`COMPANY_SPRITE_COLOUR(owner)` = `_company_colours[owner] + PALETTE_RECOLOUR_START`
(`sprite.h:20-21`), with `PALETTE_RECOLOUR_START = 0x307` (`table/sprites.h:1476`).
Separately, `DoPaletteAnimations()` rewrites palette entries 217 upward every few
ticks (`gfx.cpp:1130-1150`, `PALETTE_ANIM_SIZE_START = 217` in `gfx_type.h:231`).

Both of these operate **in index space, before anything reaches the framebuffer**.
If sprites were quantised at load time, the recolour tables would no longer find
their indices and company colours would break — and the only fix would be a
separate copy of every vehicle sprite per company colour, which is the exact
opposite of saving memory.

Applying a 256-entry LUT to the chunky framebuffer, per dirty rectangle,
immediately before c2p, leaves recolouring and palette animation working
untouched because both have already happened.

**Cost:** one byte lookup per dirty pixel.
**Benefit:** 32 colours means 5 bitplanes instead of 8 — roughly **37% less c2p
work**. Baseline for scale: a full 640×512 frame is **117.5 ms** on a calibrated
68040/25 (`PROGRESS.md`, Milestone 2 table); typical frames touch only a few
small rectangles, and `DrawSurfaceToScreen` (`amiga_v.cpp:266-294`) already
converts them individually.

Note plainly: **this phase buys speed, not RAM.** Fewer bitplanes shrinks the
Chip RAM bitmap (320×256 goes from 80 KB to 50 KB at 5 planes) and nothing else.
The chunky buffer stays 8 bits per pixel because that is what OpenTTD's blitter
writes.

### 4.2 Where the LUT goes

In `amigagfx_blit()` (`amiga_gfx.c:208-246`), between the clipping and the
`c2p_rect_asm(&args)` call at line 238.

The LUT cannot be applied in place — `g_chunky` is `_screen.dst_ptr`
(`amiga_v.cpp:312`) and OpenTTD reads it back for scrolling and for
`BM_TRANSPARENT` blends (`8bpp_simple.cpp:43` does `bp->remap[*dst]`). So:

1. Allocate a second Fast RAM buffer `g_chunky_out` of the same size, or a
   scratch buffer one dirty-rect tall.
2. For each dirty rect, copy row by row through `g_lut[]` into the scratch, then
   point `args.chunky` at the scratch and set `args.cmod` to the scratch's row
   modulo.
3. When `g_depth == 8`, skip the whole step and pass `g_chunky` directly, so the
   256-colour path costs nothing.

Inner loop should be a straight `dst[i] = lut[src[i]]` over a `w`-byte row. On
68040 this is load/index/store per byte; unrolled by 4 with `movem` staging it
should run well under the c2p it feeds. Measure it with the existing
`ReportBlitStats` counters before assuming it is free.

### 4.3 Making the bitplane count a variable

`amiga_gfx.c` hardcodes `#define DEPTH 8` at line 56. Every use:

| Line | Use |
|---|---|
| 97 | `AllocMem(g_planesize * DEPTH, MEMF_CHIP \| MEMF_CLEAR)` |
| 100 | `InitBitMap(&g_bitmap, DEPTH, w, h)` |
| 102-105 | plane pointer loop `for (i = 0; i < DEPTH; i++)` |
| 121 | `SA_Depth, (ULONG)DEPTH` (primary `OpenScreenTags`) |
| 137 | `SA_Depth, (ULONG)DEPTH` (fallback `OpenScreenTags`) |
| 149 | log line `"screen open %dx%d depth 8"` — hardcoded text |
| 182 | `FreeMem(g_chip, g_planesize * DEPTH)` |

Replace with a file-static `static int g_depth;` set from a new parameter on
`amigagfx_open(int w, int h, int depth)` (`amiga_gfx.h`), called from
`CreateMainSurface` (`amiga_v.cpp:296-322`). `amiga_v.cpp:320` also hardcodes
`"8 bitplanes"` in its `DEBUG` line.

`amigagfx_set_palette` (`amiga_gfx.c:189-206`) needs no structural change —
`LoadRGB32` with `count` = 32 or 64 works as-is — but `UpdatePalette`
(`amiga_v.cpp:210-222`) currently pushes OpenTTD's 256-entry `_cur_palette`
straight through. In reduced-colour mode it must instead load the *reduced*
palette, i.e. the RGB values of the LUT's target entries, and it must **rebuild
the LUT whenever `_cur_palette` changes** — otherwise palette animation
(`CheckPaletteAnim`, `amiga_v.cpp:224-245`) stops working, since animated
entries are re-quantised targets now. This is the subtle part of Phase 2:
`_pal_first_dirty`/`_pal_count_dirty` tell you which source entries moved;
re-running nearest-colour for just those against the fixed output palette is
cheap and keeps water and fire animating.

### 4.4 The c2p problem — there is no off-the-shelf routine

This is a real obstacle and it is not obvious until you look.

`native/c2p_glue.s` wraps `upstream/kalms-c2p/special/c2p_rect.s`, which is the
**only** rectangle-based routine in Kalms' library and is **hard-coded to 8
bitplanes**. The variable-depth routines are in `bitmap/` and `normal/`, and they
convert a whole contiguous chunky buffer, not a sub-rectangle of a wider one:

```c
void c2p1x1_6_c5_bm_040(int chunkyx, int chunkyy, int offsx, int offsy,
                        void *c2pscreen, struct BitMap *bitmap);
```

(`bitmap/c2p1x1_6_c5_bm_040.h`) — there is an offset into the *destination*, but
no chunky row modulo, so it cannot read a rect out of a 640-wide buffer.

Inventory of what exists:

- 8 planes, rect, 040: `special/c2p_rect.s` — what we use today
- 6 planes, whole bitmap, 040: `bitmap/c2p1x1_6_c5_bm_040.s`
- 6 planes, 040: `normal/c2p1x1_6_c5_040.s`
- 5 planes, 030 blitter-assisted: `normal/c2p1x1_5_c3b1_030.s`
- 5 planes, 030 / 060: `normal/c2p1x1_5_c5_030.s`, `..._060.s`
- **5 planes, rect, 040: does not exist**
- **6 planes, rect, 040: does not exist**

So Phase 2 requires either:

**(a) Adapt `c2p_rect.s`.** It is a merge network; dropping the top planes means
removing the passes that produce them and adjusting the plane pointers. Doable —
it is well-commented and the repo already assembles it with the `vasmm68k_mot`
that ships with bebbo amiga-gcc — but it is 68k assembly surgery, and it must be
validated bit-exact against a C reference the way the 8-plane path was
(`PROGRESS.md` Milestone 2 records that discipline; keep it).

**(b) Copy the dirty rect into a contiguous scratch buffer** and call the
whole-bitmap 6-plane routine on it. Simpler and safer, but the copy is an extra
pass over the pixels — and the LUT pass in 4.2 is already producing a contiguous
scratch buffer, so these two fuse into one pass. **This is the better first
implementation**: LUT and repack in the same loop, then a stock Kalms routine.
Only write assembly if measurement says the extra pass costs more than the two
saved bitplanes gain.

Note (b) also settles the depth choice: **6 planes / 64 colours is much easier
than 5 / 32**, because a stock 040-optimised 6-plane routine exists and no
5-plane 040 routine does. Unless 32 colours is needed for a specific reason,
prefer 64.

### 4.5 Which palette

`gfxdump/palette-32.json` in fact contains **27 entries**, not 32 — the
quantisation collapsed to 27 unique colours after snapping onto real TTD palette
entries. With the transparent index that is 28, comfortably inside 5 bitplanes.
`palette-ehb64.json` holds 31 base + 31 half.

For Phase 2, **EHB is the wrong target on this hardware.** EHB is an OCS/ECS
mode; the port targets AGA, where 6 bitplanes simply address 64 independent
colour registers with no half-bright constraint. The EHB sheets are interesting
if the port is ever taken to an unexpanded A500-class machine, and
`README-lores.txt` is right that they cannot go back into a standard GRF. For an
AGA/020 target, generate a fresh 64-colour palette with no half-bright
restriction — it will be strictly better than the EHB one.

Building the LUT: for each of the 256 TTD palette entries, find the nearest entry
in the output palette by squared RGB distance, and store the output *index*.
Exclusions, per section 5: leave the company-recolour destination ranges out of
the quantisation, or accept that company colours collapse into each other.

## 5. The vehicle and company-colour problem

`README-lores.txt` states this correctly and it is worth restating because it is
the one issue with no clean answer.

Company colours are applied by remapping palette indices at draw time
(section 4.1). Quantisation moves pixels onto different indices, so the remap
table no longer finds them. With an output-stage LUT the remap has *already*
happened by the time the LUT runs, so **Phase 2 as designed does not break
company colours at all** — that is the whole point of putting the LUT at the
output.

What it does break is **distinguishability**. Sixteen company colours reduced to
a 32- or 64-entry palette will collapse: two companies whose liveries differ by a
few palette steps end up identical on screen. That is a gameplay problem, not a
correctness one.

Options, honestly:

1. **Reserve indices in the output palette for the company gradients.** Take the
   16 recolour tables (`GetNonSprite(PALETTE_RECOLOUR_START + i, ST_RECOLOUR)`,
   `main_gui.cpp:402-409`), collect their destination indices, and force the
   output palette to contain a representative spread of them — quantising only
   the remaining entries. With 64 colours this is affordable: 16 companies × 2
   representative shades = 32 reserved, 32 left for the world. With 32 colours it
   is not.
2. **Accept collapse and rely on other cues.** OpenTTD already labels vehicles
   and stations with company-coloured *text*, drawn through `_colour_gradient`
   which is derived from the same tables. If the text stays distinguishable the
   liveries matter less. Cheapest option; probably adequate for single-player.
3. **Convert vehicle sprites at runtime** — the alternative raised in
   `README-lores.txt`. This means keeping vehicle sprites at full colour depth
   and quantising after recolouring, per vehicle, per company. It solves the
   problem exactly and it costs memory and time, which is what the whole exercise
   is trying to save. Not recommended.

**Recommendation: option 1 at 64 colours, option 2 at 32.** Decide the depth
first (section 4.4 argues for 64), then this follows.

## 6. Phase 3 — the interface

Fewer colours damages the UI more than the world, because the UI does not use
colours impressionistically — it uses *specific palette entries* for gradients
and highlights, and it uses them for meaning.

`SetupColoursAndInitialWindow` (`main_gui.cpp:402-409`) extracts
`_colour_gradient[COLOUR_END][8]` from byte 0xC6 of each company recolour sprite.
Those 8 shades per colour are then used for:

- every window and widget frame (`widget.cpp:202-205`) — the raised/sunken 3D
  effect is literally shades 3, 5 and 7 of one gradient
- graph axes and lines (`graph_gui.cpp:277, 576, 1302-1303`)
- smallmap owner colours (`smallmap_gui.cpp:913`)
- company text colours (`company_cmd.cpp:115-116`)
- viewport sign text (`viewport.cpp:1355`)

Quantise naively and the 8 shades of a gradient collapse to 2 or 3. Buttons stop
looking pressed. The 3D bevel disappears. This is the most visible damage of the
whole exercise and it happens instantly, on the main menu, before any game
loads.

**What would have to be done:** reserve gradient shades in the output palette
(the same mechanism as section 5 option 1), or replace `_colour_gradient` with a
hand-authored table for reduced-colour mode — 16 colours × 8 shades = 128
entries, which does not fit in 64 colours, so in practice it means cutting the
number of *distinct* window colours rather than the number of shades. OpenTTD
uses `COLOUR_END` = 16 window colours; a reduced-colour build would want maybe 4,
which means auditing every `WindowDesc` for its colour.

**Why defer it:** it is artwork and taste, not engineering, and it can only
sensibly be done once you can see the damage on a real screen. It is also
completely independent — nothing in Phases 0, 1 or 2 depends on it. And if
Phase 0 (forced zoom) is chosen over Phase 1, **the UI stays at full size and
full palette until Phase 2 turns the LUT on**, so this problem does not arise
until quite late.

Defer it, and when you do it, do it against screenshots.

## 7. Startup selection

The requirement is that the choice is made once, at startup, and the correct set
is what gets loaded — never "load full graphics then reduce", which would defeat
the memory saving entirely.

The mechanism already exists and does the right thing, because sprites are loaded
lazily from whichever set was selected before `GfxLoadSprites()` runs.

### 7.1 Order of operations at startup

From `ttd_main` (`openttd.cpp:414`):

1. `DeterminePaths(argv[0])` — `openttd.cpp:564`
2. `BaseGraphics::FindSets()` — `openttd.cpp:565`, scans for `.obg`
3. `LoadFromConfig()` — `openttd.cpp:576`, fills `BaseGraphics::ini_set`
4. `openttd.cpp:631-637`:
   ```c
   if (graphics_set == NULL && BaseGraphics::ini_set != NULL) graphics_set = strdup(BaseGraphics::ini_set);
   if (!BaseGraphics::SetSet(graphics_set)) { ... usererror("Failed to select requested graphics set '%s'", graphics_set); }
   ```
5. `GfxInitPalettes()` — `openttd.cpp:648`; blitter selection at `:652`
6. `GfxLoadSprites()` — **not called here**. First call is from
   `afterload.cpp:583` or `genworld.cpp:299`, when the intro game loads.

So the set is fixed long before any sprite is read. Nothing extra is needed.

### 7.2 The three ways to select

- **Config file.** `graphicsset` in `[misc]`, `table/settings.h:250`:
  ```
  SDTG_STR("graphicsset", SLE_STRQ, S, 0, BaseGraphics::ini_set, NULL, STR_NULL, NULL)
  ```
  It is an `SDTG_*` global-variable setting writing straight into
  `BaseGraphics::ini_set` (`base_media_base.h:162`), which is why grepping
  `settings.cpp` for it finds nothing. Bound to the `misc` group by
  `HandleSettingDescs` (`settings.cpp:1331-1333`).
- **Command line: `-I <name>`** — `openttd.cpp:460`, optformat at `:450`. Note
  it is capital I; `-G` is the map generation seed (`openttd.cpp:542`). This
  **overrides** the config key.
- **In-game, in the menu.** `SetMediaSet<T>(int)` (`settings_gui.cpp:363-376`)
  rewrites `ini_set`, calls `SetSet`, and sets `this->reload = true`. Only
  permitted when `_game_mode == GM_MENU`. Widget `GOW_BASE_GRF_DROPDOWN`,
  `settings_gui.cpp:196, 234-243, 449`.

### 7.3 What to add for the Amiga port

Very little, and this is the good news of the whole plan.

1. **Ship the lores `.obg` and its GRFs.** The dropdown in Game Options then
   lists it automatically, with no code change.
2. **Bundle `sprite_cache_size` with the choice.** This is the one thing that
   does need a small patch, because selecting a lores set is pointless without
   lowering the arena (section 0.1) and the arena is allocated once
   (`spritecache.cpp:564`). Two options:
   - Simplest and honest: document that the lores set needs
     `sprite_cache_size = 1` in `openttd.cfg`, and ship two config files.
   - Better: in `CreateMainSurface` or in `VideoDriver_Amiga::Start`
     (`amiga_v.cpp:413-448`), before `GfxInitSpriteMem` ever runs, clamp
     `_sprite_cache_size` when the selected set's `shortname` is the lores one.
     `BaseGraphics::GetUsedSet()` (`base_media_func.h:330-334`) is already
     populated by step 4 above, and the driver's `Start` runs after it.
3. **The dropdown change requires a restart**, exactly like the existing
   resolution and font behaviour. `VideoDriver_Amiga::ChangeResolution`
   (`amiga_v.cpp:595-612`) already establishes this pattern and its comment
   explains why: window layouts and glyph tables are built once at startup.
   Reuse the wording. A set change already triggers `reload` in
   `settings_gui.cpp`, but the cache arena will not resize, so print the same
   "restart to apply" note through `amigagfx_log`.
4. **If Phase 0's forced zoom is used instead of a lores set**, the selection is
   a plain boolean rather than a set name — a driver parameter
   (`-v amiga:lowmem`, parsed like `bbox` and `frameskip` at
   `amiga_v.cpp:415-423`) that raises `ZOOM_LVL_MIN` and lowers
   `_sprite_cache_size`. Much less machinery, and consistent with how the driver
   already exposes switchable behaviour so options can be evaluated in isolation.

## 8. Memory: what is actually saved, and is 8 MB reachable

### 8.1 The arithmetic

Fixed costs, independent of graphics work:

| Item | Bytes |
|---|---|
| Binary via `LoadSeg` | 5,174,152 (measured) |
| Stack (`__stack`) | 1,048,576 |
| `SpriteCache` index array | ≈ 350,000 (est.) |
| Map, 256×256 at 10 B/tile | 655,360 |
| Chunky buffer at 320×256 | 81,920 |
| Misc: strings, lang pack, windows, world objects | ≈ 300,000 (est.) |
| **Subtotal (Fast RAM)** | **≈ 7,610,000** |

Bitplanes are Chip RAM and counted separately: 320×256 at 8 planes = 81,920; at
6 planes = 61,440; at 5 planes = 51,200.

**Reading A — 8 MB total, unified.** 8,388,608 − 7,610,000 = **≈ 779 KB left**,
minus the bitplanes if Chip and Fast come from the same pool. A 4 MB sprite cache
is impossible; a 1 MB cache does not fit either. **Not reachable.**

**Reading B — 8 MB Fast plus separate Chip** (an A1200 with an 8 MB accelerator,
which is the realistic 020 target). Bitplanes come out of Chip, so the Fast
budget is 8,388,608 − 7,610,000 = **≈ 779 KB for the sprite cache**. A 1 MB cache
is just barely out of reach; 512 KB fits.

Is a 512 KB cache usable? Only with reduced sprites. As a rough scale: OpenGFX's
six GRFs total 5.1 MB *compressed on disk*, and the cache holds RLE-encoded
sprites at all four zoom levels. A 4 MB arena is the shipped default for a reason.
At 512 KB the game will run but thrash — evicting and re-decoding constantly,
which on an 020 is slow enough to be felt. With Phase 0 or Phase 1 cutting
per-sprite cost ~4×, a 512 KB arena behaves like ~2 MB, which is in the range
where it is merely tight rather than pathological.

So: **Reading B is marginally reachable, and only with both the graphics
reduction and a 256×256 map limit.** Reading A is not reachable at all.

### 8.2 What each lever is worth

| Lever | Saves | Notes |
|---|---|---|
| Lazy per-zoom encoding (Phase 0) | ~75% of cache pressure | engine-only, no assets |
| Lores GRF (Phase 1) | ~75% of cache pressure | same saving, better quality, far more work |
| Both together | ~94% | levels multiply |
| `sprite_cache_size` 4 → 1 MB | **3,145,728 B** | the actual banked saving; only safe *after* a reduction lever |
| Map 512² → 256² | 1,966,080 B | free, just a limit in the New Game GUI |
| Stack 1 MB → 256 KB | 786,432 B | needs testing — `PROGRESS.md` says OpenTTD Gurus with a small stack; find the real floor |
| 640×512 → 320×256 screen | 240 KB Fast + 240 KB Chip | already a menu option (`amiga_v.cpp:48-53`) |
| 8 → 6 bitplanes (Phase 2) | 20 KB Chip at 320×256 | trivial as memory; the win is c2p speed |
| **Stripping the binary** | **up to ~3 MB** | blocked, see 8.3 |

The ranking is worth internalising: **the binary and the stack together are 6.2 MB
and the entire graphics reduction is worth about 3 MB.** The graphics work is
necessary but not sufficient.

### 8.3 The binary — the actual blocker

`PROGRESS.md` records that `m68k-amigaos-strip` produces an executable that halts
the CPU, and `winuae/work/openttd.stripped` (6.6 MB) is a stripped artefact of an
older, larger build that was not usable.

Things to try, roughly in order of promise. All are research items — none is
known to work:

1. **Do not generate the symbols in the first place.** Verify the generated
   `objs/release/Makefile` has no `-g` (`BUILDING.md` warns that configure flags
   do not survive into the generated Makefile — grep the Makefile, never the
   configure script). Add `-g0`. This is the cleanest fix if debug info is the
   bulk.
2. **Strip at link time** with `-s`, or `-Wl,--strip-debug`, so the hunk file is
   never written with a symbol hunk that a post-hoc `strip` then mangles.
3. **`m68k-amigaos-objcopy --strip-debug`** rather than `strip`, which is less
   aggressive and may leave the hunk structure intact.
4. **Investigate why `strip` breaks it.** bebbo's toolchain goes ELF → hunk via
   `elf2hunk`; stripping the ELF before conversion is a different operation from
   stripping the hunk after. Try stripping the ELF and re-running `elf2hunk`.
5. **`-ffunction-sections -fdata-sections -Wl,--gc-sections`** to drop unreached
   code. OpenTTD 1.0.5 with networking disabled has a lot of it.
6. **Compile out more of the game.** AI (`src/ai/`), the scenario editor, NewGRF
   support, and the in-game console are each worth a measurable amount. Check
   what `--enable-dedicated` already excludes and whether any of it can be
   applied to the GUI build.

Item 1 should be tried first and takes ten minutes. If the 5.17 MB is mostly
DWARF, this whole section collapses to a solved problem and the 8 MB target
becomes comfortable rather than marginal.

### 8.4 Honest verdict

An 020 with 8 MB is **not reachable today**, because the binary alone is 5.17 MB
and the stack is another 1 MB. It becomes reachable if the binary can be reduced
to roughly 2.5–3 MB, and in that case the graphics reduction is what makes the
remaining budget comfortable rather than desperate. Pursue the binary size
first — it is cheaper to investigate, and the answer determines whether the
graphics work needs to be aggressive or merely helpful.

## 9. Ordering and risk

### 9.1 Recommended order

1. **Measure, before changing anything.** Add `GetSpriteCacheUsage()` and a peak
   watermark to `ReportBlitStats()` (`amiga_v.cpp:251-264`). Run a standard
   savegame at 320×256. Without a baseline, none of the following can be
   evaluated. *Half a day.*
2. **Try `-g0` / link-time strip** (section 8.3 item 1-2). Ten minutes to try,
   potentially worth 3 MB. Do it before anything else because the answer changes
   how hard the rest has to work. *Hours.*
3. **Phase 0: lazy per-zoom encoding**, Option B. Engine-only, no assets, no
   geometry risk, ~75% of the cache saving. *Two to three days.*
4. **Lower `sprite_cache_size` and measure again.** This is where memory is
   actually banked. Find the floor experimentally. *Half a day.*
5. **Optionally force `ZOOM_LVL_MIN = ZOOM_LVL_OUT_2X`** (`zoom_type.h:42` and
   neighbours) and look at it. One line, fully reversible. If the nearest-
   neighbour decimation looks acceptable, **Phase 1 may not be needed at all.**
   *Hours.*
6. **Phase 2: the LUT and variable bitplanes.** Start with 64 colours and the
   fused LUT+repack scratch buffer feeding stock `c2p1x1_6_c5_bm_040`
   (section 4.4 option b). Measure against the 8-plane path before writing any
   assembly. *Three to five days.*
7. **Phase 1, only if step 5's quality is rejected.** Rebuild the asset pipeline
   per sprite (section 3.1), get the GRF loading, then attack the projection.
   *Two weeks or more; see 9.3.*
8. **Phase 3: interface recolouring.** Only once there is a real screen to judge.
   *Open-ended.*

### 9.2 What can be deferred safely

- **Phase 3 entirely.** Nothing depends on it.
- **32 colours.** 64 is easier (a stock 040 c2p exists), looks better, and leaves
  room for the company-colour reservation in section 5. Drop to 32 only if
  measurement shows the sixth bitplane matters.
- **EHB.** Wrong target for AGA. Revisit only for OCS/ECS hardware.
- **The lores GRF**, if Phase 0's quality is acceptable.

### 9.3 What is much harder than it looks

Listed because each of these has a specific, identified reason.

1. **The `.nfo` geometry transformation.** It reads like "halve some numbers".
   It is actually a full asset-pipeline rewrite, because the existing sheets were
   downscaled as whole images across sprite boundaries and bled into their
   neighbours (section 3.1). The existing `gfxdump/lores-*.png` files cannot be
   re-imported as they are, at any amount of `.nfo` patching.
2. **`TILE_HEIGHT`.** It is simultaneously a world Z unit and a screen pixel
   count (`tile_type.h:20`), and halving it changes map semantics and savegame
   compatibility. The X axis halves cleanly and the Z axis does not, so the
   projection needs a divide it does not currently have (section 3.3). This is
   the single most underestimated item in Phase 1.
3. **The duplicated projection constants.** `landscape.h:52-58` and `:81-85`,
   `viewport.cpp:380-381`, `:1003-1010`, `:1678-1686` — and the scan bounds at
   `viewport.cpp:1008-1010` (`+ 95`, `>> 6`, `>> 5`) are raw pixel arithmetic
   with no shared constant. They must all move together, and getting
   `TranslateXYToTileCoord` wrong means clicks land on the wrong tile, which
   presents as "the game is broken" rather than "the graphics are misaligned".
4. **Threading zoom through the sprite cache** (Phase 0 Option B). ~100 call
   sites read `Sprite::width/height/x_offs/y_offs`. The mitigation — keep
   metadata at level-0 semantics, make only the pixel payload per-zoom — is what
   keeps this bounded, and it should be the design from the first line of code,
   not a rescue after the refactor sprawls.
5. **No 5- or 6-plane dirty-rect c2p exists.** Section 4.4. Discovering this
   halfway through Phase 2 would be expensive; the fused LUT+repack approach
   sidesteps it entirely and should be the plan from the start.
6. **Palette animation under the LUT.** `DoPaletteAnimations` rewrites entries
   217+ every few ticks (`gfx.cpp:1130-1150`). The LUT must be partially rebuilt
   on each animation step or water and fire freeze. Easy to forget, obvious in
   hindsight, and it will look like "the LUT broke the game".
7. **This toolchain miscompiles silently.** `BUILDING.md` documents three
   independent cases (`-O2` breaks C++ unwinding, `-m68040` without
   `-mhard-float` gives broken soft-float doubles, zlib above `-O0` corrupts
   data). Any new assembly, any new inner loop, any change to `spritecache.cpp`
   should be validated bit-exact against a reference the way the 8-plane c2p was
   (`PROGRESS.md`, Milestone 2). When something behaves oddly here, codegen is a
   first-class suspect, not a last resort.
